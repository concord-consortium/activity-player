### Hand the attachments manager a token source instead of a startup token

**Summary**: Learners' attachments manager gets `getTokenServiceFirestoreJWT`, which mints a new token-service JWT through the portal JWT manager on every call with a 10-second timeout, and no longer gets a startup `tokenServiceFirestoreJWT` (R2 to R8). `getAttachmentsManagerOptions` no longer awaits anything, so it becomes synchronous and `app.tsx` initializes the manager directly.

**Files affected**:
- `src/portal-api.ts`: new `refreshTokenServiceJWT`, next to `refreshActivityPlayerFirebaseJWT`.
- `src/portal-api.test.ts`: test for it.
- `src/utilities/get-attachments-manager-options.ts`: token source, no startup mint, synchronous.
- `src/utilities/get-attachments-manager-options.test.ts`: rewritten for the new shape (R9).
- `src/components/app.tsx`: call site.
- `src/components/app-auth.test.tsx`: delete the `beforeEach` default `mockGetFirebaseJWT.mockResolvedValue(["token-service-jwt"])`, which only the startup mint used.

**Estimated diff size**: ~95 lines (about 20 source, 75 test)

`src/portal-api.ts`, after `refreshActivityPlayerFirebaseJWT` (shares `kRenewalTimeoutMs`, which stays module-private):

```ts
export const refreshTokenServiceJWT = (basePortalUrl: string, rawPortalJWT: string) =>
  getFirebaseJWT(basePortalUrl, rawPortalJWT, { firebase_app: "token-service" }, kRenewalTimeoutMs);
```

`src/utilities/get-attachments-manager-options.ts`, whole file:

```ts
import { IAttachmentsManagerInitOptions } from "@concord-consortium/interactive-api-host";
import { EnvironmentName } from "@concord-consortium/token-service";
import { firebaseAppName, isAnonymousPortalData, refreshTokenServiceJWT } from "../portal-api";
import { getPortalJWTManager } from "../portal-jwt-manager";
import { IPortalData, IPortalDataUnion } from "../portal-types";

export const getAttachmentsManagerOptions = (portalData: IPortalDataUnion): IAttachmentsManagerInitOptions => {
  const { basePortalUrl } = portalData as IPortalData;
  const portalJWTManager = getPortalJWTManager();
  const getTokenServiceFirestoreJWT = basePortalUrl && portalJWTManager
    ? () => portalJWTManager.withToken(raw => refreshTokenServiceJWT(basePortalUrl, raw)).then(([token]) => token)
    : undefined;
  return {
    getTokenServiceFirestoreJWT,
    tokenServiceEnv: firebaseAppName() === "report-service-pro" ? "production" : "staging" as EnvironmentName,
    writeOptions: {
      runKey: isAnonymousPortalData(portalData) ? portalData.runKey : undefined,
      runRemoteEndpoint: isAnonymousPortalData(portalData) ? undefined : portalData.runRemoteEndpoint
    }
  };
};
```

`src/components/app.tsx` (around line 312):

```diff

-        initializeAttachmentsManager(options);
-      });
+      initializeAttachmentsManager(getAttachmentsManagerOptions(getPortalData() as IPortalDataUnion));
```

Tests (R9), each with the mutation it catches:

| Test | Asserts | Fails if |
|---|---|---|
| anonymous: passes no token or token source | `toStrictEqual({ getTokenServiceFirestoreJWT: undefined, tokenServiceEnv: "staging", writeOptions: { runKey, runRemoteEndpoint: undefined } })` | a token or source is passed for anonymous runs; `writeOptions` changes |
| learner: passes a token source and no token, without minting | `toStrictEqual({ getTokenServiceFirestoreJWT: expect.any(Function), tokenServiceEnv: "staging", writeOptions: {...} })`; `mockRefreshTokenServiceJWT` not called | `tokenServiceFirestoreJWT` comes back; the options mint at startup |
| learner: mints a new token-service JWT with the current portal JWT on every call | first call resolves `token-service-jwt-for-launchPortalJWT`; after `now += 49 min`, the second resolves `...-for-refreshedPortalJWT`; the mock was called with `(basePortalUrl, "launchPortalJWT")` then `(basePortalUrl, "refreshedPortalJWT")`; `mint` called once | the raw portal JWT is captured when the options are built; the source caches its first token (R4) |
| learner: rejects when the mint fails | `mockImplementationOnce(() => Promise.reject("Portal error"))`; the source rejects with `"Portal error"` | the source swallows the failure (R6) |

`toStrictEqual` is used rather than `toEqual` because `toEqual` treats an `undefined` property as absent, so it could not tell a dropped `tokenServiceFirestoreJWT` key from one passed as `undefined`. The timeout is asserted in the `portal-api.test.ts` test, where the superagent mock can see it.

### Verify a long session on the dev server (R10, no commit)

**Summary**: Before merge, checks the first acceptance criterion against the real manager, portal and token service using a fake browser clock. Nothing is committed.

1. Run AP on port 8081 (port 8080 is usually another dev server): `npm start -- --port 8081`, after the bump step's `npm install`.
2. Launch a staging learner run of an activity with an audio-enabled open response (the only question-interactive that uses attachments), and in the AP tab's address bar replace `https://activity-player.concord.org/branch/master/` with `http://localhost:8081/`, keeping the query string, within the launch token's 180-second life. A Playwright `route` on the AP URL does not catch the launch, because the portal reaches AP through an HTTP redirect, so the host is changed by hand. A local load is recognizable by having no `firebase_app=token-service` request at startup.
3. With Playwright, launch Chromium with `--use-fake-ui-for-media-stream --use-fake-device-for-media-stream` so recording works without a microphone, install the clock before navigating, and use `setSystemTime` to move it (not `fastForward` or `runFor`, which fire the 20-minute idle detector):

```js
await page.clock.install();
await page.goto(launchUrl);
// ...load the page with the recording: one GET api/v1/jwt/firebase?firebase_app=token-service
await page.clock.setSystemTime(Date.now() + 56 * 60 * 1000);
// ...switch to another page and back: portal JWT refresh, new token-service mint, credentials 200
await page.clock.setSystemTime(Date.now());
// ...switch pages again: no mint, the new token on the credentials call, S3 206
```

Switching pages remounts the interactive, which requests the attachment URL again; reloading the page would start a new launch with an expired launch token.

4. Pass: after the jump, the attachment request makes a portal JWT refresh (`api/v1/jwt/portal`) and a new `firebase_app=token-service` request, and the token service answers that token's `credentials` call with 200; after the reset, the next request makes no mint, sends the same token, and S3 serves the attachment. While the clock is ahead, S3 rejects the read (Chrome reports `net::ERR_BLOCKED_BY_ORB`) because the URL is signed with the advanced browser clock; that failure is expected and is why the clock goes back.

This procedure passed on 2026-10-06 against a staging learner launch, with `8e67401` on the dev server and `0.13.0-pre.0` from npm. The first attachment read minted the first token-service JWT. After the 56-minute jump, the next read refreshed the portal JWT, minted with the refreshed portal JWT, and the token service accepted the new token. After the reset, the next read made no mint, sent the same token on `credentials`, and S3 served the recording (206). An existing recording was enough: every check is a read, so the fake-media flags were not needed.

## Open Questions

### RESOLVED: Judgment call: a `portal-api.ts` helper, or call `getFirebaseJWT` directly?
**Options considered**:
- A) `refreshTokenServiceJWT` in `portal-api.ts`, beside `refreshActivityPlayerFirebaseJWT`.
- B) Call `getFirebaseJWT` from the options file with an exported timeout constant.

**Decision**: A. `kRenewalTimeoutMs` stays a single private value shared by every renewal, the mint matches the existing `refresh*` naming, and the timeout is testable where the superagent mock lives. B would export the constant for one caller.

### RESOLVED: Judgment call: make `getAttachmentsManagerOptions` synchronous?
**Options considered**:
- A) Synchronous, returning the options directly.
- B) Keep it `async` with nothing awaited.

**Decision**: A. With the startup mint gone it awaits nothing, and an `async` signature would keep the `.then` in `app.tsx` for no reason. It has one caller.

### RESOLVED: Judgment call: commit the pre-release pin, or wait for 0.13.0?
**Options considered**:
- A) Commit `0.13.0-pre.0`, verify, then move the pin to `0.13.0` before merge.
- B) Develop on the yalc link only and commit the bump once 0.13.0 is out.

**Decision**: A. The branch then builds in CI and on any checkout with `npm ci`, and R1 already requires the final pin before merge, which the "Pin the final interactive-api-host 0.13.0" step makes.

### RESOLVED: Low confidence: which staging activity exercises attachments for R10?
**Context**: The verification step needs a staging activity, assigned to a test learner, whose interactive writes and reads attachments (audio recording or image upload).
**Options considered**:
- A) An existing staging activity with such an interactive.
- B) Author a one-page activity on staging for this check.

**Decision**: A, falling back to B. Of the question-interactives, only `open-response` uses attachments: with `audioEnabled` authored, recording calls `writeAttachment` and playback calls `getAttachmentUrl` (`packages/open-response/src/components/runtime.tsx`). Any staging activity with an audio-enabled open response, assigned to a test learner, serves; if none exists, a one-page activity with one is quick to author. Recording needs a microphone, so the run uses a Playwright-launched Chromium with `--use-fake-ui-for-media-stream` and `--use-fake-device-for-media-stream`, which supply a synthetic microphone without a permission prompt.

### Second round (2026-10-06, against the published `0.13.0-pre.0`)

Roles: Release Engineer, QA Engineer, Senior Engineer, Security Engineer.

Verified without a finding: the plan's R9 and `refreshTokenServiceJWT` tests, written out as throwaway files, pass (7) against the npm package, and each fails under its mutation (source caches its first token, static token re-added, timeout dropped, failure swallowed, startup mint, portal JWT captured at build); dropping the `basePortalUrl` check fails the type check. Suggested resolution: R5 says each portal request in the call is bounded, so the call settles, without a number.
**Resolved**: R5 rewritten as suggested.
